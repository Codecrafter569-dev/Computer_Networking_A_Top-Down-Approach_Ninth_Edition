# Chapter 2 Notes: Transport Gaps, App-Layer Protocols & HTTP

---

## 1. Simple Meaning

**Services not provided by transport protocols:** TCP and UDP (the two Internet transport protocols) are good at some things but they simply don't promise everything an app might want — like guaranteed speed or built-in security.

**Application-layer protocols:** These are the "rulebooks" that apps like browsers, email clients, and messaging apps follow so two programs on different computers can talk and understand each other.

**HTTP:** The specific rulebook used by web browsers and web servers to request and send web pages.

---

## 2. Why It Matters

- Every app you build (Android, backend, API) sits on top of TCP/UDP. Knowing what they *don't* give you tells you what *you* must handle yourself (e.g., adding TLS for security, or handling delay for a video call app).
- HTTP is the backbone of REST APIs, web scraping, mobile app networking (Retrofit/OkHttp in Android use HTTP under the hood).
- Debugging with tools like `curl`, Postman, or browser DevTools only makes sense once you understand HTTP request/response structure.

---

## 3. Core Idea (Step by Step)

### A) What transport protocols do NOT provide
TCP gives you: reliable delivery, in-order delivery, flow control, congestion control. But TCP does **not** guarantee:
- **Timing** — no promise about *how fast* data arrives (bad for live voice/video where delay matters more than perfection).
- **Minimum throughput** — no guaranteed bandwidth; congestion control can throttle your connection.
- **Security** — data travels in plaintext, visible to anyone snooping the network.

UDP gives even less: no reliability, no ordering, no flow/congestion control — and it *also* doesn't provide timing, throughput guarantees, or security.

Because of this gap, apps must add what they need:
- Need security → add **TLS/SSL** on top (e.g., HTTPS = HTTP + TLS + TCP).
- Need timing for real-time media → apps like Zoom/Skype build their own timing logic on top of UDP, tolerating some loss instead of waiting for retransmission.

### B) Application-layer protocols
An application-layer protocol defines four things:
1. **Types of messages** exchanged (e.g., request, response).
2. **Message syntax** — what fields exist and how they're separated.
3. **Message semantics** — what the info in each field means.
4. **Rules** for when and how a process sends/responds to messages.

Two kinds:
- **Public-domain protocols** — defined in RFCs, open to everyone (HTTP, FTP, SMTP). This is why any browser can talk to any web server.
- **Proprietary protocols** — closed, undisclosed (older Skype used one).

Note: an app needs more than just its protocol — e.g., the Web needs HTTP *plus* a standard for how pages are structured (HTML).

### C) Network apps covered in the book (roadmap)
Chapter 2 walks through real protocols as case studies: the Web (HTTP), file transfer (FTP), email (SMTP/POP3/IMAP), DNS, video streaming, P2P apps, and finally socket programming (writing your own client/server in UDP and TCP).

### D) The Web and HTTP
- **HTTP** = HyperText Transfer Protocol — client-server model. Browser (client) requests; web server responds with **objects** (HTML file, image, video, etc.).
- A **web page** = one base HTML file + several referenced objects, each with its own URL.
- HTTP uses **TCP** as its transport — so it inherits reliable, in-order delivery for free; HTTP itself doesn't worry about lost/corrupted data.
- HTTP is **stateless**: the server doesn't remember anything about past requests from a client. Even if you ask for the same page twice, the server treats it as brand new each time. (State like login sessions is added separately via **cookies**.)

## 4. Key Terms

| Term | Meaning |
|---|---|
| Timing guarantee | A promise about how fast data will be delivered — TCP/UDP don't give this |
| Throughput guarantee | A promise of minimum bandwidth — not given by TCP/UDP |
| TLS/SSL | Security layer added on top of TCP to encrypt data |
| Application-layer protocol | Rules defining message types, syntax, semantics, and send/respond timing |
| RFC | Request For Comments — official document defining a public protocol |
| Socket | The "door" through which a process sends/receives data over the network |
| HTTP | Protocol used to fetch web pages/objects |
| Object | A file (HTML, image, video) addressable by a URL |
| Base HTML file | The main HTML document that references other objects on a page |
| Stateless protocol | Server keeps no memory of past client requests |
| Non-persistent connection | A new TCP connection is opened for every single object |
| Persistent connection | One TCP connection is reused for multiple objects/requests |
| RTT | Round-Trip Time — time for a small packet to go to server and back |
| Pipelining | Sending multiple HTTP requests back-to-back without waiting for each response |
| Request line | First line of an HTTP request: method + URL + version |
| Status line | First line of an HTTP response: version + status code + phrase |
| Header lines | Extra info in a message (Host, Content-Type, Date, etc.) |
| Entity body | The actual data/content carried in the message (e.g., form data in POST, the file in a response) |

## 5. How It Works (Flow)

### Non-persistent HTTP (old style, HTTP/1.0 default)
1. Client opens a **TCP connection** to server (takes 1 RTT).
2. Client sends an HTTP **request** for one object over that connection.
3. Server sends the **response** with that object, then **closes** the connection.
4. For every other object on the page (images, etc.), steps 1–3 repeat — a brand-new TCP connection each time.
5. Browsers often open **parallel connections** to fetch several objects at once and cut total time.

### Persistent HTTP (default in HTTP/1.1)
1. Client opens **one** TCP connection.
2. Client sends request 1 → gets response 1, connection **stays open**.
3. Client sends request 2 (can even send it without waiting for response 1 — **pipelining**) → gets response 2.
4. This repeats for all objects on the page over the **same** connection.
5. Connection closes only after being idle for a configured time.

### HTTP message structure
**Request message:**
```
GET /somedir/page.html HTTP/1.1
Host: www.example.com
Connection: close
User-agent: Mozilla/5.0
Accept-language: en

(entity body — used with POST/PUT)
```
- Line 1 = request line: **method**, **URL path**, **HTTP version**.
- Common methods: GET, POST, HEAD, PUT, DELETE.
- Then header lines, a blank line, then optional body.

**Response message:**
```
HTTP/1.1 200 OK
Date: ...
Server: Apache
Last-Modified: ...
Content-Length: 6821
Content-Type: text/html

(entity body — the actual HTML/file data)
```
- Line 1 = status line: **version**, **status code**, **status phrase**.
- Common codes: 200 OK, 301 Moved Permanently, 400 Bad Request, 404 Not Found, 505 HTTP Version Not Supported.

## 6. Real Example

When you open an Amazon product page:
- Browser opens a TCP connection to Amazon's server.
- It sends a `GET /product/xyz HTTP/1.1` request → gets back the base HTML.
- The HTML references 20+ objects (product photos, CSS, JS). With **persistent HTTP**, the browser reuses the same connection (or a few parallel ones) to fetch all of them quickly, instead of reconnecting 20 times.
- Because HTTP is stateless, Amazon uses a **cookie** (a header field) to recognize you're logged in across requests.

## 7. Mini Implementation Idea (Termux-friendly)

1. **Inspect real HTTP messages:**
   ```
   curl -v https://example.com
   ```
   `-v` shows the exact request line, headers, response status line, and headers — matches everything in section 5.

2. **Manually send a raw HTTP request** (great for understanding the format by hand):
   ```
   printf 'GET / HTTP/1.1\r\nHost: example.com\r\nConnection: close\r\n\r\n' | nc example.com 80
   ```
   You'll literally see the server's status line + headers + body.

3. **Write a tiny Python HTTP client from scratch** using raw sockets (no `requests` library) — builds the request line and headers yourself, sends over a socket, reads the response. This directly shows you're doing what a browser does under the hood.

4. **Run a local server** and watch requests arrive:
   ```
   python -m http.server 8080
   ```
   Then `curl -v http://localhost:8080/` and watch the terminal log the incoming request.

## 8. Common Mistakes

- Thinking TCP guarantees **fast** delivery — it only guarantees reliable, in-order delivery, not speed or bandwidth.
- Confusing a **persistent TCP connection** with the server "remembering" you — persistence is just connection reuse; state (login, cart) needs cookies.
- Assuming HTTP/1.1 always opens a new connection per object — by default it's **persistent**.
- Forgetting that HTTP itself has no encryption — security only exists if TLS (HTTPS) is added.
- Mixing up **status line** (response) with **request line** (request) — different first lines for different message types.

---

## 9. Memory Hook

**TCP = a reliable courier** who promises your package arrives complete and in order — but never promises *how fast*, and never locks the box (no encryption).

**Non-persistent vs persistent HTTP = phone calls:** non-persistent is hanging up and redialing after every single sentence; persistent is one call where you say everything, then hang up.

**HTTP message = an order slip:** request/status line = the order itself, headers = special instructions, blank line = end of the slip, body = the actual item/payment.

---

## 10. Ultra-Short Revision

- TCP/UDP don't guarantee timing, bandwidth, or security — apps add these themselves (e.g., TLS for security).
- App-layer protocols define message types, syntax, semantics, and send/respond rules; can be public (RFC-based) or proprietary.
- HTTP is a stateless, client-server protocol running over TCP, used to fetch web objects.
- Non-persistent HTTP opens a new TCP connection per object; persistent HTTP (HTTP/1.1 default) reuses one connection, optionally with pipelining.
- HTTP request = request line + headers + blank line + optional body; HTTP response = status line + headers + blank line + body.

## 11. Interview / Exam Questions

1. **What key services does TCP fail to provide?**
   Timing guarantees, minimum throughput guarantees, and security (encryption) — apps must add these themselves if needed.

2. **What four things does an application-layer protocol define?**
   Message types, message syntax, message semantics, and rules for when/how to send or respond.

3. **Why is HTTP called a stateless protocol?**
   Because the server does not retain any information about previous client requests — each request is handled independently.

4. **What is the main difference between non-persistent and persistent HTTP connections?**
   Non-persistent opens a separate TCP connection per object; persistent reuses one TCP connection for multiple objects/requests, reducing overhead.

5. **What are the components of an HTTP request message?**
   A request line (method, URL, version), header lines, a blank line, and an optional entity body.
